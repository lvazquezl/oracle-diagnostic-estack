# Capability Matrix

Vista legible de [`config/capability-matrix.yaml`](../config/capability-matrix.yaml), que es la **fuente estructurada de verdad**. Este Markdown debe mantenerse consistente con el YAML — ver `tests/test_capability_matrix_registry_consistency.sh`. Consumida por el gate `version`/`architecture` de todo Workflow Contract (`docs/CONTRACTS.md#workflow-contract`) y por `policies/version-awareness-policy.md`.

## Leyenda

| Status | Significado |
|---|---|
| `PLANNED` | La feature Oracle existe en esa versión, pero el e-stack aún no tiene contrato/skill/query ni siquiera registrado para ella. |
| `FOUNDATION_ONLY` | El dominio tiene agente/contrato/skills `registered`, pero ningún skill materializado (`status: active`) cubre esta versión todavía. |
| `PARTIAL` | Al menos un skill materializado cubre esta versión, pero no el dominio completo. |
| `SUPPORTED` | Cobertura completa certificada (no ocurre aún en Fase 1/Hardening, salvo `/change` como proceso). |
| `UNSUPPORTED` | La feature Oracle **no existe** en esa versión/arquitectura — no es una limitación del e-stack. |
| `LICENSE_DEPENDENT` | Depende de licenciamiento adicional (Diagnostics/Tuning Pack, etc.) independientemente de la cobertura del e-stack — ver `policies/licensing-awareness-policy.md`. |

`latest` trackea la versión mayor soportada más reciente (hoy: 23ai) hasta que se agregue una nueva vía `/change compatibility`.

## Notas por dominio

- **Oracle Core**: `SUPPORTED` desde Fase 2 — las 18 skills `oracle/*` completamente materializadas (`SKILL.md` + `manifest.yaml`), ~20 queries `Q-ORA-*` certificadas (Query Contract v2), 40 tests dedicados. `oracle/diagnostics` (ADR) requiere 11g+; en 10g esa sub-capacidad específica degrada a `UNSUPPORTED` sin afectar el resto del dominio.
- **Performance**: `SUPPORTED` desde Fase 3 — 31 skills `performance/*` completamente materializadas (`SKILL.md` + `manifest.yaml`), catálogo `queries/performance/**` (21 queries certificadas, Query Contract v2 + Query Variant Contract). Esta fila mide el core no licenciado (ruta estándar sin Diagnostics Pack, Statspack); AWR/ASH/ADDM son capacidades `LICENSE_DEPENDENT` independientes, filas propias abajo.
- **AWR/ASH/ADDM**: requieren Diagnostics Pack en todas las versiones donde existen (10g+) — `LICENSE_DEPENDENT` no es una limitación del e-stack sino del contrato de licenciamiento del cliente; ver `policies/licensing-awareness-policy.md`. Los 3 skills (`performance/awr-analysis`, `performance/ash-analysis`, `performance/addm-analysis`) están completamente materializados y funcionan cuando la licencia se confirma.
- **Statspack**: `SUPPORTED` desde Fase 3, cobertura multi-sección completa desde Fase 3 Completion Hardening — no requiere licencia adicional; `skills/performance/statspack-analysis` cubre Load Profile, Instance Efficiency, Top Wait Events, SQL ordered by CPU/elapsed/executions/gets/reads, Instance Activity, Library Cache, Latch, Enqueue, I/O (incl. ASM), Memory/Cache Sizes, Redo/Commit y Parsing derivados, vía consulta en vivo (`Q-PERF-WAIT-STATSPACK-001`, sólo wait events) y vía ingesta de reporte texto (`parsers/performance/statspack_parser.py`). Cobertura por-sección es `SUPPORTED`/`PARTIALLY_SUPPORTED`/`UNSUPPORTED` según el reporte concreto suministrado — ver `docs/PHASE_3_COMPLETION_HARDENING.md#gap-1--statspack-completion`.
- **RAC**: `SUPPORTED` desde Fase 4 (11gR2–23ai) — 19 skills `rac/*` completamente materializados (topología, servicios, session distribution, load balancing CLB/RLB, interconnect, Cache Fusion, recursos Clusterware). 10g/11gR1 (CRS legacy) no certificado → `PLANNED` (la feature Oracle sí existe), no `UNSUPPORTED`. RAC deep performance (impacto de `gc *` en DB Time) `DELEGATES_TO_PERFORMANCE`, no se duplica en este dominio. **RAC detection** básica sigue `SUPPORTED` desde Fase 2 vía el Target Profile.
- **GI (Grid Infrastructure)**: `SUPPORTED` desde Fase 4 (11gR2–23ai) — absorbido por `oracle-rac-analyst` (sin agente separado), 12 skills `rac/gi-*` materializados (version, node-status, resource-status/-properties, scan, vip, listeners, network-interfaces, ocr-status, voting-status, cluster-health, configuration-consistency). Como marca/arquitectura formal es 11gR2+ (antes: Oracle Clusterware) → `UNSUPPORTED` en 10g. OCR/Voting repair explícitamente `PROHIBITED` (sólo visibility).
- **ASM**: `SUPPORTED` desde Fase 4 (11gR2–23ai) — 12 skills `asm/*` completamente materializados (topología, diskgroups, capacidad real vía `USABLE_FILE_MB`, redundancia, salud de discos, failure groups, rebalance), reemplaza el `asm/capacity.md` plano de Foundation. 10g fuera de soporte activo (arquitectura de disk group difiere significativamente antes de 11g). ASM write operations explícitamente `PROHIBITED`. **ASM detection** básica sigue `SUPPORTED` desde Fase 2.
- **Multitenant**: `SUPPORTED` desde Fase 6 (12.1–23ai) — 26 skills `multitenant/*` completamente materializados (architecture, cdb-discovery, pdb-inventory, pdb-state, pdb-open-mode, pdb-services, pdb-rac-placement, pdb-sessions, pdb-tablespaces, pdb-temp, pdb-undo, local-undo, parameters, common-local-users, common-local-roles, components, plugin-violations, resource-usage, resource-manager, lockdown-profiles, application-containers, proxy-pdb, configuration-drift, healthcheck, assessment, troubleshooting), 15 queries `Q-CDB-*` certificadas. `Local Undo` no existe en 12.1 (introducido en 12.2) — degradado vía Query Variant Contract, nunca asumido. `Application Containers`/`Proxy PDB` (12.2+) son `PARTIALLY_SUPPORTED` (topología vía `V$PDBS`, sin profundidad de lifecycle). No existe antes de 12c → `UNSUPPORTED` real (no es una limitación del e-stack); en `NON-CDB` (cualquier versión) `MULTITENANT_STATUS: NOT_APPLICABLE` se publica directamente desde el Target Profile sin activar el agente. Más de 1 PDB por CDB es `LICENSE_DEPENDENT` según edición — señalado por finding específico, no a nivel de dominio completo. **Container detection** básica sigue `SUPPORTED` desde Fase 2 vía el Target Profile. Ninguna ejecución de `ALTER PLUGGABLE DATABASE`/`CREATE`/`DROP`/`CLONE`/`UNPLUG`/`PLUG`/`SAVE STATE`/cambio de parámetro/Resource Manager/lockdown profile/usuario común o local — sólo visibilidad y diagnóstico. **PHASE 6 — QUERY COMPATIBILITY & DICTIONARY CERTIFICATION HARDENING**: 3 sub-capacidades con precisión de versión distinta del agregado 12.1–23ai — PDB Saved State `SUPPORTED` desde **12.1.0.2** (patch level; no existe en 12.1.0.0/12.1.0.1; vista real `DBA_PDB_SAVED_STATES`, no `CDB_PDB_SAVED_STATES`, que no existe — verificado, 404 en docs.oracle.com); PDB Resource Metrics `PARTIALLY_SUPPORTED` en 12.1 / `SUPPORTED` en 12.2+ (`V$RSRCPDBMETRIC` introducida en 12.2.0.1, sin fuente alternativa certificada para 12.1); Plug-in Violations `SUPPORTED` con variantes version-specific (12.1 sin `CON_ID`, `container_id: NOT_AVAILABLE`; 12.2+ con `CON_ID`). Ver `docs/PHASE_6_QUERY_COMPATIBILITY_HARDENING.md`. **Versión futura**: mismo criterio que Data Guard Fase 5 — la columna "latest" arriba deja de decir `SUPPORTED`, declara `COMPATIBILITY_VALIDATION_REQUIRED`; `agents/oracle-multitenant-analyst/manifest.yaml#supported_versions` declara esa familia `UNKNOWN_FUTURE`, `config/capability-matrix.yaml` declara `future_status: COMPATIBILITY_VALIDATION_REQUIRED` en la fila `multitenant`, y todas las queries `Q-CDB-*` en `config/query-compatibility-matrix.yaml` usan un `max` explícito (`"23.0"`, nunca `latest`).
- **Data Guard**: `SUPPORTED` desde Fase 5 (10g–23ai) — 21 skills `dataguard/*` completamente materializados. Foco principal `PHYSICAL_STANDBY`; `LOGICAL_STANDBY`/`SNAPSHOT_STANDBY`/`FAR_SYNC` reconocidos pero `PARTIALLY_SUPPORTED` (sin análisis profundo específico en esta fase). Switchover/failover **execution** `PROHIBITED` — sólo readiness/visibility. Active Data Guard (lectura en standby) es `LICENSE_DEPENDENT`, señalado por finding específico vía `ACTIVE_DATA_GUARD_CHECK`. **Role detection** básica sigue `SUPPORTED` desde Fase 2 vía el Target Profile. **Versión futura (PHASE 5 — DATA GUARD FINAL PROCESS-VIEW & PORTABILITY HARDENING, `# 15-16`)**: la columna "latest" arriba deja de decir `SUPPORTED` — desde este hardening declara explícitamente `COMPATIBILITY_VALIDATION_REQUIRED` (no una reinterpretación por comentario, un cambio estructural real). "23ai" es la última major *certificada*; una major Oracle futura y aún desconocida nunca hereda soporte — `agents/oracle-dataguard-analyst/manifest.yaml#supported_versions` declara esa familia como `UNKNOWN_FUTURE`, `config/capability-matrix.yaml` declara `future_status: COMPATIBILITY_VALIDATION_REQUIRED` en la fila `dataguard`, y todas las queries `Q-DG-*` en `config/query-compatibility-matrix.yaml` usan un `max` explícito (`"23.0"` o `"12.1"` según variante, nunca `latest`) para que el Query Variant Resolver nunca resuelva una major desconocida como compatible por herencia. Una major nueva requiere `/change compatibility` antes de certificarse en cualquiera de estas cuatro fuentes.
- **Network**: `SUPPORTED` desde Fase 4 (10g–23ai) — 14 skills `network/*` completamente materializados (Oracle Net, listeners, SCAN, SCAN resolution, service registration, LOCAL/REMOTE_LISTENER, connection path, TNS errors, timeouts, name resolution, interconnect, healthcheck, troubleshooting), reemplaza el `network/tns.md` plano de Foundation. SCAN es exclusivo de RAC 11gR2+; el resto del dominio aplica igual en Standalone. Ningún cambio de configuración de red/DNS/firewall/listener ejecutado (`PROHIBITED`).
- **RMAN / Backup & Recovery**: `SUPPORTED` desde Fase 7 — 30 skills `rman/*` completamente materializados (`SKILL.md` + `manifest.yaml`), catálogo `queries/rman/**` (14 queries certificadas, Query Contract v2 + Query Variant Contract). RMAN execution (BACKUP/RESTORE/RECOVER/DELETE/CROSSCHECK/CHANGE/CONFIGURE/CATALOG/UNCATALOG/DUPLICATE/SWITCH DATABASE/ALLOCATE CHANNEL) explícitamente `PROHIBITED` — sólo visibilidad, readiness y runbooks manuales (`execution_status: NOT_EXECUTED`). PDB PITR/multitenant-awareness son sub-capacidades `PARTIALLY_SUPPORTED` (no certificadas al detalle completo por versión) sin afectar el resto del dominio. Reemplaza la fila `PARTIAL` de Foundation (sólo `rman/backup-status.md` materializado, plano).
- **OS, Capacity, Documentation**: un skill representativo materializado por dominio; el resto `registered` (ver `skills/REGISTRY.md`). OS y Documentation no dependen de la versión Oracle — la tabla los repite igual en las 8 columnas por consistencia estructural con el resto de la matriz.
- **/change**: el proceso de gobierno está completo y probado (`tests/test_change_governance_flow.sh`) independientemente de la versión del target — es un proceso sobre el propio e-stack, no sobre el ambiente Oracle.

## Actualización

Toda incorporación de una nueva versión Oracle o ampliación de cobertura de un dominio entra vía `/change compatibility` o `/change skill`/`/change query`, actualizando **ambos** archivos (`config/capability-matrix.yaml` y este Markdown) en el mismo cambio — ver `EVOLUTION.md#13-change-compatibility`.
